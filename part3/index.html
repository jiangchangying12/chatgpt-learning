Part 3
Search、Deep Research 與 Files

這一章不只教你「何時按哪個功能」，而是建立一條可追溯的證據鏈：問題需要什麼資料、來源是否可靠、內外部資訊如何組合、結論是否真的被證據支持。

完成標準
85 分 + 實作

能設計來源策略、區分三種能力、檢查引用是否支持結論，並完成一份混合內部檔案與外部資料的分析。

版本註記：依 2026 年 9 月官方 OpenAI 文件編寫；實際功能依方案與工作區可能不同。

SEARCH

快速查找與核實

適合現況、版本、公告、單一或少量明確事實。重點是快速找到權威原始來源。

DEEP RESEARCH

多來源整合

適合需要拆解問題、蒐集多方資料、比較矛盾證據、產生完整且可追溯報告。

FILES

你的專屬證據

適合需求書、會議紀錄、Excel、程式碼與內部報告。外部搜尋無法取代你的內部事實。

不是三選一：「最新 .NET 升級對內部系統的影響」通常需要 Search 取得官方現況、Files 讀取內部依賴，再用推理建立影響映射；若範圍廣、來源多，才升級成 Deep Research。

02｜先用四個問題選擇工作方式

判斷問題偏向方式陷阱
答案會隨時間改變嗎？Search「最新」只是訊號，仍要限定來源與日期。
是否需要多來源完整研究？Deep Research不是每個搜尋都值得啟動完整研究。
主要證據是否在我的資料裡？Files先說明各檔案版本、用途與優先順序。
是否同時有內部與外部證據？組合工作流清楚標註哪個結論來自哪一類來源。

可直接使用的來源策略 Prompt

在開始研究前，先不要回答結論。
請先提出來源策略：
1. 哪些問題可用穩定知識回答？
2. 哪些需要目前的外部資料？
3. 哪些只能從我提供的檔案判斷？
4. 每類資料優先使用哪些原始／官方來源？
5. 哪些結論需要兩個以上獨立來源？
6. 若證據衝突或不足，如何標示而不是自行補齊？

03｜有引用，不代表已證實

逐項檢查引用

  1. 來源真的談到該結論嗎？
  2. 是原始來源還是轉述？
  3. 日期與版本仍適用嗎？
  4. 引用支持整句，還是只支持其中一部分？
  5. 來源是否存在利益或範圍限制？

區分四種敘述

  • 來源事實：文件直接記載
  • 推論：由多項事實推導
  • 假設：為推進工作暫時採用
  • 建議：基於目標與取捨提出
PDF 常見錯誤：摘要正確不代表頁碼、表格關聯或例外條款都正確。重要需求應要求引用原文位置，並回到檔案人工抽查；掃描品質差時要先確認 OCR 結果。

04｜六個實用案例

案例 1

查目前 .NET LTS

Search。優先 Microsoft 官方支援政策與版本頁。輸出同時標示查詢日期，避免答案日後失效。

案例 2

150 頁需求書找矛盾

Files + reasoning。先建立需求 ID、版本優先級與矛盾類型；沒有外部標準需求時，不必先搜尋網路。

案例 3

PostgreSQL HA 選型

Deep Research + Files。外部研究方案、RTO/RPO 與限制；內部檔案提供人力、預算、機房與採購條件。

案例 4

消防系統介接規範

官方 Search + Files。外部 API 現行版本與內部介接設計分開取證，再產生欄位與錯誤碼差異表。

案例 5

水情資料異常

Files／Data 優先。先看原始資料、時間範圍與品質規則；搜尋只能補充背景，不能證明內部資料異常原因。

案例 6

法規符合性

官方來源 + 人工權責。AI 整理條文、版本與差異；法務或權責單位做最終解釋與核准。

05｜實作：升級影響研究

任務

評估某 ASP.NET Core + PostgreSQL 系統升級到目前支援版本的影響。準備一份內部架構／依賴清單作為 Files，外部資料只採官方文件。

交付物

  1. 研究問題與範圍
  2. 來源策略表：問題、來源類型、優先來源、查詢日期
  3. 內部依賴與外部版本差異矩陣
  4. 相容、需修改、未知、待測試四類結論
  5. 至少 8 個驗證測試
  6. 不可由 AI 決定的 3 個事項
每個結論標註：外部來源／內部檔案／推論／假設。
引用必須直接支持相鄰結論。
若官方資料與內部文件衝突，不要靜默合併；
建立「衝突—可能原因—影響—確認責任」表。
完成證據：拿掉結論文字後，第三人仍能從來源與推導欄位重建你的判斷；這才叫可追溯。
